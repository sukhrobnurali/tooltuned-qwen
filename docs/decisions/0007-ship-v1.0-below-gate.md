# ADR 0007 — Ship v1.0 below the BFCL gate with honest disclosure

- **Status:** Accepted
- **Date:** 2026-05-14
- **Decision driver:** Brief §4.4 (BFCL +3pp gate) + ADR 0006 (locked diagnosis: tuned LoRA over-calls on irrelevance) + the realisation that Phase 3.5 alone is unlikely to clear the gate against the strong in-tree base of 86.68%.

## Context

The project's terminal artifact gate is brief §4.4: tuned model must beat base by ≥3pp on BFCL before the adapter is promoted on the public HF main repo. Two Phase 4 evals (S9, S10) produced delta ≈ -7.64pp under the in-tree V3 evaluator. ADR 0006 locked the diagnosis: 76% of the regression comes from over-calling on `irrelevance` / `live_irrelevance` because the xLAM training set has zero negative examples by design.

The straightforward remediation — Phase 3.5 with a ~25% synth-irrelevance mixin — is scoped in ADR 0006. Honest gate math there shows:

- Plausible best case post-3.5: ~86% tuned overall = -0.5pp delta. **Still under the +3pp gate.**
- The realistic outcome is ~-3pp delta even with the fix.

This is because the in-tree V3 base measurement (86.68%) is much higher than the brief's stated V4 leaderboard baseline (50.3%), and the gate was anchored against the latter when ADR 0001 was written. The gate threshold should have been recalibrated against the in-tree base once it was known (S8) — that's a process miss, not a code bug.

Three options to close the project:

1. **Ship below gate with honest disclosure.** Document the regression, the diagnosis, the planned-but-deferred fix. Frame as rigorous methodology including failure analysis. No further Colab burn.
2. **Phase 3.5 → ship whatever delta comes out.** ~25-35 Colab units, ~30-40 min training + ~80 min eval. Probably still under gate. Adds 1-2 sessions.
3. **Re-calibrate the gate via brief amendment.** Pick a sub-metric that does pass (e.g. AST-only — but that's also negative; or `live_relevance` recall — but cherry-picking single categories looks bad). Defensible only if there's a principled re-statement of what the gate is measuring.

## Decision

**Ship v1.0 below the BFCL gate with full honest disclosure (option 1).** Phase 3.5 + the canonical-CLI revival + a BFCL leaderboard submission move to a documented roadmap; v1.0 is the snapshot the user can point to as a portfolio piece.

The brief's gate is NOT amended — the original +3pp target stands as the design intent. v1.0 publishes below it, and that fact is documented prominently on the public HF card, in the GitHub README, and in this ADR.

The shape of the disclosure is operationalised in [docs/superpowers/specs/2026-05-14-ship-v1.0-design.md](../superpowers/specs/2026-05-14-ship-v1.0-design.md) — that spec drives the actual ship session (S11 in the project's session log).

### Why ship below gate rather than chase it

1. **Phase 3.5 mathematically doesn't clear the gate.** ADR 0006's honest gate math projects best-case tuned overall at ~86%, which is -0.5pp delta. The Colab cost (~25-35 units) doesn't buy us a "pass" outcome; it buys us a smaller miss.
2. **The portfolio value of a rigorous failure analysis is high.** A reviewer who sees ADRs 0001-0006, the in-tree evaluator with documented limitations, the locked diagnosis with per-category numbers, and the honest disclosure walks away thinking "this person knows how to do ML rigorously and is honest about results." That's a stronger signal than a marginal "barely cleared the gate" result on a hand-wavy eval.
3. **The brief's discipline is preserved.** §16.2 (no AI attribution) is clean across all 13 commits this session. §16.4 (commit style) is followed. §16.6 (zero AI-attribution leakage) audit returns zero hits. The brief stays unamended; we just publish v1.0 below the gate it defines, with disclosure.
4. **Time-on-project hit a natural ceiling.** The user has been working on this for almost a week across 10 sessions. The marginal value of a +1 training run is small; the marginal cost of "another two sessions to maybe still miss the gate" is large.
5. **Phase 3.5 stays scoped.** The remediation isn't abandoned — it's a documented ADR 0006 spec with a Phase 3.5 yaml config sketched. A future contributor (or future-user) can pick it up by reading ADR 0006 + the project memory. v1.0 is the inflection point where active development closes.

### Why not re-calibrate the gate

A re-stated gate that just happens to pass would look like cherry-picking to any senior reviewer. The principled re-statement options:

- AST-only sub-gate: still -3.8pp, doesn't pass.
- "Positive recall" sub-gate (must_call category): +11.1pp, but it's a single 18-item category — too narrow to be a credible standalone gate.
- Macro-average across sections instead of micro-average: same denominator problem.

None of these survive scrutiny. Honest disclosure of the failure under the original gate is the more defensible posture for a portfolio piece.

## Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| Run Phase 3.5 first, then decide | The decision is binary now: ship as-is, or commit another ~1 day. ADR 0006's math is convincing enough that the empirical Phase 3.5 number is unlikely to change the outcome. Faster to commit now. |
| Hide v1.0 entirely (remove the public HF adapter) | Loses the portfolio value of the published artifact. The HF repo is already public + indexed; pulling it would look more like a cover-up than an honest ship. |
| Run Phase 3.5 in a sub-1-day form, ship "validated diagnosis" | Tempting — would convert ADR 0006's diagnosis from hypothesised to empirically validated. Rejected because (a) the per-category data already pins the diagnosis tightly enough for a portfolio claim, and (b) the user's explicit framing was "what we have done so far" — they want to finalise, not iterate. |
| Pull the v1.0 adapter, publish only the GitHub repo + ADRs | Loses the HF model card as a publicly defensible artifact; fragments the project's surface area. Inferior to "ship with honest disclosure." |
| Wait for Phase 5 (merged weights, GGUF) before tagging v1.0 | Phase 5 deliverables are convenience artifacts, not gate items. They can ship as v1.1 if the user wants to pick them up later. Coupling them to v1.0 delays the close indefinitely. |

### Roadmap (not v1.0, documented as future work)

- **Phase 3.5:** synth-irrelevance generator + retrain, per ADR 0006. Spec is written, code is not.
- **Canonical bfcl-eval CLI:** revive when upstream vllm/transformers/torch/NCCL conflicts resolve. Code path is preserved at `eval/bfcl_runner.py`, `notebooks/colab_bfcl.ipynb`.
- **BFCL leaderboard PR:** only if/when a future re-train clears the gate.
- **Phase 5 (merged weights, GGUF for ollama/llama.cpp):** convenience artifacts, not gating; can ship as v1.1 separately.
- **Phase 6 / 7 (README polish on HF, blog post, leaderboard PR):** subsumed by v1.0 except the leaderboard PR.

### Process lessons (one-paragraph each, kept terse)

1. **Calibrate the gate against the actual evaluator before training.** ADR 0001 anchored against the brief's 50.3 V4 number, but the in-tree V3 evaluator with lenient parallel scoring produces base ≈ 87%. The threshold should have been re-anchored after S8 produced the actual base measurement, not held fixed at +3pp on top of a different evaluator's number. Worth carrying into future fine-tune projects: *if the eval pipeline changes, recalibrate the success criterion before continuing.*

2. **Positive-only datasets create over-call bias.** Obvious in hindsight; not obvious before the per-category breakdown showed it. The fix (synth negatives from the same data) is straightforward and scoped in ADR 0006. Worth carrying into future fine-tunes: *if the dataset has no negatives for a decision-to-act category, the model will learn to always act.*

3. **Eval methodology decisions are gating decisions.** ADR 0005 documented the V3-vs-V4 + lenient-parallel + in-tree-vs-canonical choices. Without those documented, the v1.0 numbers would be uninterpretable and the failure would look like a code bug. Worth carrying: *document the evaluator's limitations as load-bearing context, not footnotes.*
