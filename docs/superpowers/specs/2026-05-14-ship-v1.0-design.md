# Ship plan — v1.0 as an honest portfolio piece

- **Date:** 2026-05-14
- **Status:** Approved (brainstorm output, ready for implementation in S11)
- **Companion decision record:** [ADR 0007](../../decisions/0007-ship-v1.0-below-gate.md)
- **Implementation session:** S11 (fresh session)

## Goal

Close the project out as a publicly defensible portfolio piece. The BFCL gate failed (-7.64pp, see [ADR 0006](../../decisions/0006-eval-debugging.md)); we publish v1.0 with full honest disclosure rather than chasing the gate. No more Colab budget burned. Single focused session, ~1.5-2 hours of work.

## Out of scope (locked)

- No Phase 3.5 training run. Diagnosis stays as documented hypothesis backed by per-category data.
- No brief amendment. The +3pp gate stands as the original target; v1.0 publishes below it with disclosure.
- No new evals. Numbers we have are the numbers we ship.
- No re-architecture of `eval/`, `training/`, or `hub/` modules.

## Deliverables (11 items)

### 1. Patch `src/tooltuned_qwen/hub/model_card.py`

Currently the card renders a "TBD until Phase 4" placeholder when `bfcl_results` is None; when present, it renders a results table. The behaviour needs one extra branch: when `bfcl_results['delta'] < 0.03`, render the results table AND prepend a disclosure callout block.

Callout block content (suggested wording, finalise in implementation):

```markdown
> **Gate disclosure (v1.0):** This adapter is published below the +3pp BFCL gate
> defined in the project brief (delta -7.64pp on the in-tree V3 evaluator). The
> regression is concentrated in `irrelevance` / `live_irrelevance` categories
> (-29 of -38 lost items) — see [ADR 0006](https://github.com/sukhrobnurali/tooltuned-qwen/blob/main/docs/decisions/0006-eval-debugging.md)
> for the locked diagnosis and the Phase 3.5 remediation spec (deferred for v1.0).
```

Code change: ~10-15 LoC in `generate_card`. Optional helper `_format_gate_callout(delta)` returning the markdown block when delta < threshold, empty string otherwise.

**Tests:** one new test in `tests/test_model_card.py` asserting the callout appears in the rendered card for `delta = -0.0764` and is absent for `delta = 0.04`. Existing tests must continue to pass.

### 2. Generate BFCL comparison artifacts locally

Add a small CLI entry-point (could be inline in step 4's publish script, no need for a separate file) that calls:

```python
from tooltuned_qwen.eval.compare import build_comparison
build_comparison(
    base_results=base_results,    # loaded from results/bfcl_intree/base/results.json
    tuned_results=tuned_results,  # loaded from results/bfcl_intree/tuned/results.json
    out_dir="results/bfcl_intree/comparison",
    base_model_name="Qwen/Qwen3.5-4B",
    title="BFCL V3 single-turn — base vs. fine-tuned Qwen 3.5 4B (in-tree eval)",

```

Produces `bfcl_results.json` + `comparison.md` + `bfcl_comparison.png` under `results/bfcl_intree/comparison/`. Commit all three.

### 3. README.md rewrite on GitHub repo

Replace the current init-level README with a portfolio-grade one-pager. Structure (target ~250-400 lines, GitHub-flavoured markdown):

- **Header / pitch:** one sentence + key links (HF model, ADRs, results)
- **Headline numbers:** small results table — overall, plus per-section split (AST cats / must_call / must_not_call). Mark the gate result HONESTLY.
- **Motivation:** why fine-tune Qwen 3.5 4B for function calling, what the brief asked for.
- **Methodology:** dataset choice (xLAM, why over Hermes), training config (LoRA r=16, bf16, single A100 epoch), evaluation methodology (in-tree V3 evaluator, why not canonical CLI). Link each to its ADR.
- **Results:** per-category table from `comparison.md`. Embed `bfcl_comparison.png`.
- **Honest analysis:** the regression. The diagnosis (over-call on irrelevance). The supporting evidence. The Phase 3.5 remediation that exists as a written spec but wasn't run for v1.0. Link to ADR 0006.
- **Lessons learned:** 3-5 bullets. Examples: (a) positive-only training data creates over-call bias; (b) base-model evaluation upfront would have caught the gate-too-tight problem before training; (c) canonical CLI install fragility vs in-tree pivot tradeoffs; (d) per-category eval > overall-only.
- **Reproducibility:** `uv sync`, notebook entry points, dataset access, BFCL hosting.
- **What's NOT in v1.0:** explicit list — Phase 3.5 retrain, canonical bfcl-eval CLI path, BFCL leaderboard submission. These are roadmap, not bugs.
- **References:** ADRs 0001-0007, HF model, dataset, brief, eval framework.

Tone: lab-notebook honest, not marketing. The reader should walk away thinking "this person knows how to do ML rigorously and is honest about results", not "this person ships hype".

### 4. `scripts/_publish_v1_card.py`

One-shot script (not a notebook, not a module) that:
1. Loads `results/bfcl_intree/comparison/bfcl_results.json`
2. Calls `generate_card(bfcl_results=..., training_config_path="configs/default.yaml", out_path="MODEL_CARD.md")`
3. Uploads `MODEL_CARD.md` as `README.md` to the HF main repo
4. Uploads `results/bfcl_intree/comparison/bfcl_comparison.png` to the HF main repo
5. Prints the live HF URL on success

Uses `HfApi(token=os.environ["HF_TOKEN"])` per the Phase 1.3 finding #7 pattern. Idempotent — re-runs overwrite cleanly. User runs once locally with their HF_TOKEN.

Filename starts with underscore by project convention (cf. `scripts/_build_intree_notebook.py`) — these are one-shot maintenance scripts, not library code.

## Risks

1. **`generate_card` schema mismatch with current `comparison.py` output.** Low probability — the schema contract is documented at the top of `model_card.py` and `compare.py::build_comparison` was written to produce that exact dict. Mitigation: run a unit-test round-trip in step 1 of the implementation (already covered by `test_card_renders_with_bfcl_results`).

2. **HF token plumbing breaks again on the publish.** Phase 1.3 finding #7 (sticky HF token cache). Mitigation: `_publish_v1_card.py` constructs `HfApi(token=os.environ["HF_TOKEN"])` explicitly, no global state.

3. **README too long or too defensive.** Risk of over-explaining the negative result. Mitigation: lab-notebook tone, lead with results, let the methodology speak. Aim for 250-400 lines, not 800.

4. **Forgetting to delete the smoke repo before publishing the v1.0 tag.** Low cost to fix after the fact, but cleaner if done before the tag. Mitigation: smoke-repo deletion appears as step 11 in the implementation order, before the tag.
